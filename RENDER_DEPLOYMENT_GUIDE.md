# Render deployment guide

This repository is prepared for a new Render production environment. No Render account, paid service, domain, or production database was created or changed during preparation. The first Blueprint sync provisions paid resources, so review the plans and current [Render pricing](https://render.com/pricing) in the dashboard before applying it.

## Before you start

- Push this repository to a Git provider connected to your Render account.
- Choose the Singapore region for backend, worker, and database; private service networking requires a shared region.
- Decide whether to provide a Gemini API key. Without one, the assistant follows the application's safe fallback; document embedding requires credentials to complete successfully.
- Keep payment and subscription providers set to `DEMO`. This deployment does not process live payments.
- The app has no email delivery integration. Invitation/reset links are not emailed.
- Do not import the local demo database. Production starts on the new empty managed database.

## Create the services

1. In Render, create a Blueprint from the connected repository and select `render.yaml`.
2. Review all four services and their paid plans. Confirm the new database is named `supportiq-db`, is PostgreSQL 16 in Singapore, and has no public IP allow-list entries. Render uses `ipAllowList: []` to disable external database access; application services connect over the private network.
3. When prompted for `FRONTEND_ORIGIN` and `FRONTEND_URL`, enter the exact HTTPS origin Render assigned to `supportiq-frontend` (no trailing slash). If Render has not assigned the static-site URL yet, complete the first sync, read its URL from the dashboard, then set both values and redeploy the backend and worker.
4. Leave Gemini variables blank until you have a real key. Never paste keys into this repository. Render-generated JWT and webhook secrets are generated by the Blueprint.
5. Apply the Blueprint only after reviewing costs. This is the first external action; it is not performed by this preparation.

The static site builds with `npm ci && npm run build`, publishes `frontend/dist`, and rewrites unknown SPA paths to `/index.html`; asset paths, including `/supportiq-widget.js`, remain available. Vite receives the backend public URL at build time. Render serves the frontend globally, so the browser calls the backend's public HTTPS URL. The worker and API use the database's private connection string. See [Render Blueprints](https://render.com/docs/blueprint-spec), [private networking](https://render.com/docs/private-network), and [static site redirects and rewrites](https://render.com/docs/redirects-rewrites).

## Verify after provisioning

1. Wait for backend health at `https://<backend-host>/api/v1/health`; require a successful response with database status `UP`.
2. Open the frontend root and direct routes `/pricing`, `/platform`, `/chat/<company-slug>`, and `/orders/<company-slug>`; each should serve the SPA. Test a real company slug after registration.
3. Confirm `https://<frontend-host>/supportiq-widget.js` returns JavaScript.
4. In browser developer tools, verify API requests target the backend HTTPS host and WebSocket connects to `/ws` using `wss://`. Render supports WebSockets on web services; connections are subject to its idle timeout and reconnect behavior. See [Render WebSockets](https://render.com/docs/websocket).
5. Register a test company, configure its widget, upload a small policy document (with Gemini credentials configured), and verify it reaches `READY`. Invite a test agent and verify the role-restricted workspace.
6. Keep payment providers in DEMO and verify that checkout pages clearly remain simulated. Do not run live transactions.
7. Check Render logs for successful Flyway V1–V6 migrations and startup. Do not copy secret values into tickets or logs.

## Approved deployment workflow

The GitHub workflow `.github/workflows/production-deploy.yml` is manual and targets a GitHub Environment named `production`. Configure that environment with required reviewers before use. Add `RENDER_API_KEY` as a protected secret, and add the backend, worker, and frontend service IDs and health/site URLs as environment variables according to the workflow file. The workflow deploys the approved commit and runs health and route checks. Do not put Render deploy hooks or API keys in repository variables or files. Render's API deploy endpoint is documented [here](https://api-docs.render.com/reference/create-deploy).

## Domains and operations

A custom domain is optional for initial validation. Add one only after the first deployment is healthy, then update `FRONTEND_ORIGIN` and `FRONTEND_URL` to the final frontend origin and redeploy. Configure DNS and TLS in Render's dashboard.

Set alerts in Render for failed deploys, repeated restarts, high memory/CPU, database storage/connection pressure, and worker failures. The application logs use structured JSON in production. Public widget and chat endpoints should be placed behind an edge/WAF rate policy before substantial public traffic; current database-backed limits cover authentication and order lookup, not all public chat traffic. Review [Render metrics and alerts](https://render.com/docs/metrics) and [logging](https://render.com/docs/logging).
